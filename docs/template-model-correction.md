# Correcting the Pages/Templates duplication

Started 2026-08-13. This file is the running record for the model correction:
Landing Page "Pages" and "Templates" become one concept, quiz visual templates
become manageable records, and both deployment editors return to the requested
information architecture.

Every claim below was measured in this codespace and the command that measured
it is given.

---

## What was wrong, measured

Three exploration passes read the tree before anything was changed. The
duplication is real and it has a precise shape.

### Landing Pages had two template systems side by side

| Surface | Backed by | Count |
|---|---|---|
| `Pages` tab | `funnel-landing-pages` rows | 3 seeded samples |
| `Templates` tab | `listLpTemplates()` — a **code** catalogue | 12 |
| Deployment picker | `funnel-landing-pages` rows | the same 3 samples |

`LandingPagesApp.tsx:1045-1049` is the tab bar, and the `Templates` count was
`EXPECTED_LP_TEMPLATE_COUNT` — a registry constant, not a content count,
because the two tabs were counting different things. `TemplateLibrary.tsx:228`
calls `listLpTemplates()` and is passed **no `onUse` handler** from either app,
so the catalogue was browse-only by construction. The twelve templates could be
looked at and never chosen.

The deployment picker (`LandingPagesApp.tsx:706`) selected a *Page* row, so the
three sample pages were the entire universe of deployable landing pages:

    src/components/builder/lp/section-copy.ts:140-151
    MVA Pain First   mva-pain-first   template_id: human_recovery_story
    Authority Build  authority-build  template_id: authority_network
    Editorial Test   editorial-test   template_id: editorial_investigation_v2

### Quizzes had the same shape

`QuizBuilderApp.tsx:123-127` — `Quiz Builder | Deployments | Templates`, with
`Templates` again a browse-only view of `listQuizTemplates()` (20 code entries).
The deployment editor's real template choice lived on the `Render & Embed` tab
as a grid over `QUIZ_TEMPLATES` (`QuizBuilderApp.tsx:515-523`), which is a
second, disconnected presentation of the same twenty.

### The quiz deployment editor's information architecture

`QuizBuilderApp.tsx:421-428`, verbatim before this change:

    basics · render (Render & Embed) · destinations · chrome (Header / Footer)
    · sections (Body Sections) · tracking (Tracking & Pixels)

### The landing-page deployment editor had no tabs at all

Worth recording because the correction brief assumed it mirrored the quiz one.
`LPDeploymentEditor` (`LandingPagesApp.tsx:658`) was a single 720px card with
seven stacked fields. So requirement 5 is not a rename on that side — the
tabbed shell has to be built.

## The end state, as a data model

    Landing Page:  LP Template  ×  Quiz Flow  ×  Brand  ×  Deployment config
    Quiz:          Quiz Flow    ×  Quiz Template  ×  Brand  ×  Deployment config

There is no `LP Page × LP Template` any more. The authored reusable object and
the template are the same object.

### One authoritative set, with renderers still in code

The twelve landing-page templates and twenty quiz templates are ported design
work. Their markup and their token tables must stay in code — they are
generated from the handoff and regenerated by `scripts/extract-lp-templates.mjs`.
What they lacked was a manageable *record*: you cannot disable, clone or delete
a module export.

So the split is:

    CODE  (renderer definitions, generated, immutable)
      PORTED_TEMPLATES   12   src/lib/lp-templates/
      LP_IDENTITIES       4   src/lib/lp-identities/
      QUIZ_TEMPLATES     20   src/lib/quiz-templates/model.ts

    DATABASE  (the authoritative manageable set — what the product offers)
      funnel-landing-pages    LP templates       template_id  -> a code renderer
      funnel-quiz-templates   quiz templates     renderer_key -> a code renderer

`src/lib/template-registry.ts` keeps its job unchanged: it answers "does this
renderer id resolve". It stops being a user-facing catalogue. Every product
surface — the Templates lists, both deployment galleries, the preview and the
public renderer — reads **records**. That is the single authoritative set the
brief requires, and the reason the code libraries are allowed to remain.

### Why `funnel-landing-pages` is reused rather than replaced

A new `funnel-lp-templates` collection would be a third landing-page template
system during the migration and would orphan every `funnel_lp_deployments`
row's `landing_page_id` foreign key. The rows already carry exactly the fields
a template needs — `name`, `slug`, `template_id`, `sections` — so the
collection is not changing shape, it is being told what it always was. The UI
label becomes "Landing Page Templates"; the slug stays for referential
stability.

## Schema changes

### `funnel-landing-pages` (LP templates)

| field | type | why |
|---|---|---|
| `is_enabled` | checkbox, default true | selectability for **new** deployments |
| `origin` | select `stock`/`clone`/`blank`/`ai`/`legacy` | provenance, and how reconcile recognises a stock row |
| `stock_key` | text, indexed | the registry slug a stock row was materialised from; makes reconcile idempotent |
| `archived_at` | date, nullable | soft delete when a deployment still references the row |
| `slot_overrides` | jsonb | template-level content for the twelve ported templates |

**`is_enabled` is not `is_published`, and the asymmetry is deliberate.**
Enabling a template writes `is_enabled: true` *and* `is_published: true`.
Disabling writes `is_enabled: false` and **leaves `is_published` alone**, because
the brief requires that "existing deployments using a disabled template may
continue rendering with a visible administrative warning". `is_published` is
the render gate (`lp-deployment.ts:169`); `is_enabled` is the selectability
gate. Collapsing them would take a live page down as a side effect of tidying a
library.

`slot_overrides` is what makes a ported template editable. The twelve render
through `PortedTemplateView`, which deliberately offers no element tree — the
markup is the handoff's bytes and a click-to-edit that cannot write would be a
lie. But `src/lib/lp-slots/` already extracts 1,046 named slots across the
twelve, and `composeTemplate` already joins parts with overrides. The rendering
half was built and had no editing surface; `content-actions.ts` had a complete
server layer with **no caller anywhere in the repo**. Template-level slot
overrides are the missing half, and they compose with the per-deployment ones:

    composeTemplate(template, { ...template.slot_overrides, ...deployment.content_overrides })

Template defaults are the reusable copy; deployment overrides are the per-brand
copy. Deployment wins. Neither is brand-specific in the template itself, which
is what keeps a template brand-neutral after being previewed under a brand.

### `funnel-quiz-templates` (new)

| field | type | why |
|---|---|---|
| `name` | text, required | |
| `template_id` | text, required, unique index | **the stable id stored on deployments** |
| `renderer_key` | text, required | which code renderer draws it; validated against the registry |
| `code`, `blurb` | text | catalogue display |
| `is_enabled` | checkbox, default true | selectability |
| `origin` | select `stock`/`clone`/`blank` | provenance |
| `stock_key` | text, indexed | reconcile idempotency |
| `archived_at` | date | soft delete |
| `config_overrides` | jsonb | progress-form default and other presentation choices |

The twenty stock rows are seeded with `template_id === renderer_key === 'sq_*'`,
so **every existing `funnel_quiz_deployments.template_id` keeps resolving with
no data rewrite**. A clone gets a new `template_id` and keeps the source's
`renderer_key`, which is the whole reason the two fields are separate: a clone
is a new selectable identity drawn by an existing renderer.

### `funnel-lp-deployments`

| field | type | why |
|---|---|---|
| `destination_overrides` | jsonb | the `Destination URL's` tab |
| `utm`, `pixels` | jsonb | the `Tracking & Pixels` tab |

These three did not exist on the LP side. The tabs the brief asks for have no
content without them, and an LP deployment that embeds a quiz genuinely
delivers leads and fires pixels, so the settings belong to it.

### What is *not* added

There is **no `render_mode` on LP deployments.** A landing page is a standalone
page; an embed mode would be the "meaningless mode merely for visual symmetry"
the brief names. What sits above the LP gallery on General instead is the
optional embedded-quiz-template override, shown with the recommendation the
chosen LP template makes, which is the real per-deployment presentation choice
on that side.

### Quiz deployment chrome columns

`header_config`, `footer_config` and `body_section_overrides` stay in the
database and stop being read or written. Dropping the columns would destroy
data irreversibly; continuing to read them would be exactly the "hidden
duplicate" the brief forbids — chrome that Brand Identity owns, still being
overridden invisibly per deployment. They are marked deprecated and hidden.
**This is a visible change**: a deployment that carried custom chrome now
renders the brand's. That is the intent of the requirement, and it is reported
rather than smoothed over.

## Sample-record reconciliation

`MVA Pain First`, `Authority Build` and `Editorial Test` are removed from the
seed constants and from the database — but not blindly.

`mva-pain-first` is **published and deployed live at `/c/pain`**, and
`seedStarterFunnelsForBrand` points every new brand's starter deployment at it
(`funnel-samples.ts:232-257` hard-codes the slug). Deleting the row would break
those deployments' foreign keys.

The reconcile therefore works by **identity-preserving repoint**:

1. Each sample row already carries a `template_id` naming a real stock
   template (`human_recovery_story`, `authority_network`,
   `editorial_investigation_v2`).
2. Every deployment pointing at a sample row is repointed to the **stock
   template row carrying that same `template_id`**.
3. Only then is the sample row deleted.

Because the renderer id is identical on both sides of the repoint, **no
deployment changes appearance**. That is what makes this legal under "do not
silently change an existing deployment to another template" — nothing about
the rendered template changed; a wrong-model record stopped standing between
the deployment and the template it was already using.

A sample row is only recognised as sample data when its slug, name and
`template_id` all match the seed constants. A row whose content was edited is
kept and re-labelled `origin: 'legacy'`, because at that point it is user
content wearing a sample's name.

## Fail visibly

`resolveForRender` returns a stand-in and a `usedFallback` flag. That was an
improvement over silence, but the brief is explicit: "Unknown/missing template
IDs must fail visibly. Never silently render the first template."

So the deployment render paths stop accepting a stand-in. If a stored template
id resolves to no enabled record, `resolveLpDeployment` / `resolveQuizDeployment`
return **no deployment**, the public router falls through to its existing
not-found path, and the failure is logged under one grep-able prefix. The
admin lists and both galleries badge the deployment in red naming the exact
unresolvable id.

Serving a *different* law-firm template than the one an operator chose is worse
than serving nothing, on a legal-advertising page, which is why refusal is the
right side of that trade.

## The architecture review broke this design twice before it was built

An adversarial reviewer was given the design above and the acceptance criteria,
told to refute them, and given no description of the implementation. Eight
claims went in. Two came back broken in ways that would have taken every live
funnel landing page to a 404, and five more needed changing. All are fixed; the
design text above has been corrected in place, and what it got wrong is here.

| # | Claim | Verdict | What changed |
|---|---|---|---|
| 1 | Reusing `funnel-landing-pages` is safe | **broken** | `deleteLP` cascade-deleted every referencing deployment. Survivable when a row was one brand's page; a template is shared by every brand and the collection is `isAuthenticated` with no Site on it, so one operator tidying the library could take down another tenant's live pages. `deleteLP` and `cloneLP` are deleted, not wrapped. |
| 2 | The sample repoint is identity-preserving | **broken** | `lp-deployment.ts:172` refused any landing page whose row had no `sections`. The twelve ported templates have none by construction. Repointing `/c/pain` onto a stock row would have 404d it. The gate is now asked of the renderer that reads sections. Metadata was a second, quieter half: `lpDeploymentMeta` read the hero section, so every stock-template page would have got a canned description — it reads slots now. |
| 3 | Disabling leaves live pages rendering | **broken, and self-contradictory** | The design's own "fail visibly" section had the render path consult `is_enabled`, which is exactly the thing the `is_enabled` section forbade. The render path consults existence only. `is_enabled` is enforced at publish and nowhere else. |
| 4 | Template-level slot overrides are safe | survives on XSS and byte-parity, **broken on preflight** | `composeTemplate` escapes every override identically whatever its origin, so a merged map is just more overrides. But the preflight validated only the deployment's half, so a template-level override naming a dead slot passed and landed silently in `unknownOverrides` at render. It validates the merge now. |
| 5 | A clone can share a `renderer_key` | **broken** | Six places treated a stored quiz `template_id` as one of the twenty code ids, so a clone could not be saved or published by any door. Validators check SHAPE; existence is checked where a database read is safe. The reviewer's argument against an async validator is recorded in `src/lib/template-records/id.ts` and was decisive: it runs inside the write transaction, and on a database where the migration has not run it would throw — turning a skipped migration into a total write outage, while the resolvers deliberately degrade to a 404. |
| 6 | Refusing to render is safe | **survives** | Verified: a clean 404 on the same tenant, no crash, no cross-tenant fall-through, and `generateMetadata` agrees. |
| 7 | Chrome falls back to the brand | **broken claim** | It fell back to *nothing*. There was no brand-chrome branch anywhere, so dropping the deployment reads would have removed the entire header and footer — including `brand.legal.copyright`, which on an attorney-advertising page is a compliance-visible regression rather than a cosmetic one. Brand Identity gained real `defaultHeader` / `defaultFooter` before the deployment reads were removed. |
| 8 | — | — | Also raised: one row is now what every tenant renders from on an `isAuthenticated` collection. Bounded by refusing to delete a referenced template and archiving stock rows rather than dropping them. Not fully closed — see "Not done". |

## What the tests found that review did not

The identity suite runs against a real database, and three of its findings were
invisible to every pure test and to the review:

* **The sample retirement never ran.** `isUnmodifiedSampleSections` compared
  `JSON.stringify` output, and Postgres normalises `jsonb` without preserving
  key insertion order. All three samples read as "edited by an operator" and
  were kept. Keys are sorted before comparison now; array order stays
  significant, because a reordered list of settlement figures IS an edit.
* **`FunnelQuizDeployments` still validated against the code registry**, so a
  cloned template could not be attached to a quiz deployment. Only the
  landing-page half of finding 5 had been repaired.
* **`progress_form` was read by `QuizRuntime` and never set** on the resolved
  deployment, so the override an operator could edit reached the public page as
  `undefined` on every request since it shipped.

## What the browser found that nothing else could

Three of these were passing every structural check at the moment they were
broken, which is the whole argument for the browser suite existing.

* **The landing-page gallery cards painted nothing.** Each mounted its template
  in an `<iframe srcdoc>`. The iframe existed, had the right bounding box, and
  its `contentDocument` reported 1172px of real content — so a count, a
  measurement and a DOM read all passed while the card was solid black. It
  renders blank in this Chromium with and without `sandbox`, with and without
  `contain: paint`, with `zoom` in place of `transform`, and at native width
  with no transform at all. `docs/production-readiness.md` records this same
  gallery falling into the same trap once before, which is why the fix is not a
  fifth measurement: previews now mount through `PortedTemplateView` — the
  component the public page and the builder's centre pane already render — and
  the suite samples the card's PIXELS.
* **`SectionHeading` dropped its marker attribute.** It rendered
  `data-section-heading={id}` and every caller passed no `id`, so React omitted
  the attribute entirely and two whole tabs reported having no structure while
  plainly showing it. Derived from the title now.
* **Three overlays were anonymous `div`s.** `ConfirmDialog`, `Modal` and the LP
  preview cover the viewport and swallow clicks, so they are the elements most
  in need of announcing what they are. All three carry `role`/`aria-modal`/
  `aria-label` now.

### And two of the suite's own claims were false

Worth recording separately, because a test that lies is worse than no test.

* **`fetch` silently drops a `Host` header.** It is forbidden by the fetch spec
  and undici discards it without error, so the public-render proof sent every
  request as `Host: 127.0.0.1:3000`, resolved to the fallback site, and compared
  two pages that were not the ones under test — while reporting success. `curl`
  honours the header, which is how the discrepancy surfaced. It uses `node:http`
  now, and asserts the strong property: each page must carry its OWN template's
  headline copy and not the other's. A length comparison alone would never have
  caught the old fallback, because it made both pages identical.
* **The cross-tenant assertion was asking for a regression.** It keyed on HOST,
  but the resolver matches on `(site, path)` deliberately, so a deployment is
  reachable on every domain its own Site owns. Rewritten to key on site.
